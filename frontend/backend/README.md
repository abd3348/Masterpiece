# Campus Mate - ASP.NET Core MVC

تطبيق محلي على **.NET 10 + MVC + Razor + EF Core 10 + SQL Server**، مرتبط بقاعدة `MasterDB` والواجهة الحالية.

## التشغيل

من مجلد المشروع الرئيسي:

```powershell
dotnet run --project backend/CampusMate.csproj --launch-profile CampusMate
```

افتح [الموقع المحلي](http://localhost:5080). يمكن أيضًا فتح `CampusMate.slnx` في Visual Studio، أو تشغيل `Start-CampusMate.ps1`.

تحتاج .NET SDK 10 وSQL Server محليًا. الاتصال في `backend/appsettings.json` يستخدم حساب Windows الحالي:

```text
Server=.;Database=MasterDB;Integrated Security=True;Encrypt=True;TrustServerCertificate=True
```

لتغيير الاتصال دون حفظ كلمة مرور في الكود:

```powershell
$env:ConnectionStrings__CampusMate = 'your connection string'
dotnet run --project backend/CampusMate.csproj --launch-profile CampusMate
```

## القاعدة وبيانات التطوير

المخطط يُدار الآن بواسطة **EF Core Migrations** و`Data/AppDbContext.cs`. قاعدة `MasterDB` الموجودة اعتُمدت بعد مطابقة الجداول الـ23 وأعمدتها ومفاتيحها وفهارسها وقيودها، دون إعادة إنشائها. جدول `sysdiagrams` الخاص بـSQL Server بقي خارج موديل التطبيق.

لقاعدة جديدة، غيّر الاتصال ثم شغّل `dotnet ef database update --project backend/CampusMate.csproj` من جذر المشروع. لا تحتاج تشغيل `database/schema.sql`؛ بقي كمرجع تاريخي وتوثيقي. لا يوجد تعديل تلقائي للجداول أثناء بدء التطبيق. خطوات Visual Studio وقاعدة موجودة أخرى في [دليل Migrations](../docs/DATABASE_MIGRATIONS.md).

Development يضيف بيانات العرض فقط إذا كان Users فارغًا؛ لا يعيد ضبط البيانات الموجودة أو كلمات المرور. كلمات المرور في SQL مجزّأة بواسطة `PasswordHasher` ولا تظهر في استجابات API.

حسابات البداية في التطوير، وكلمة مرورها `Campus123`:

| الدور | البريد |
| --- | --- |
| مستأجر | tenant@campus.test |
| مستأجر ثانٍ | tenant2@campus.test |
| مالك | owner@campus.test |
| إدارة | admin@campus.test |
| زملاء سكن بحسابات فعلية | ahmad@campus.test / yazan@campus.test / mahmoud@campus.test |

هذه حسابات تطوير؛ Production لا يضيفها تلقائيًا. المستخدم الحقيقي يستطيع إنشاء ملف زميل عبر حفظ تفضيلات المشاركة.

## تنظيم MVC وRazor

- `Views/Home/Index.cshtml`: مدخل الموقع والحالة المشتركة والتنقل.
- `Views/Public`, `Auth`, `Tenant`, `Landlord`, `Admin`: **36 شاشة `.cshtml` فعلية**.
- `Views/Shared/_ScreenLayout.cshtml`: هيكل مشترك وعنوان وخصائص الشاشة من `ViewModels/ScreenViewModel.cs`.
- `ScreensController`: يعرض الشاشة من قائمة مسارات محددة ويفحص الدور قبل عرض الصفحات الخاصة.
- `Controllers`: الحسابات والعقارات والإيجارات والمجتمع والوسائط ورسوم النشر.
- `Services`: قواعد العمل وتحويل بيانات SQL إلى DTOs الواجهة.
- `Models`: كيان مستقل لكل جدول من جداول التطبيق الـ25، بما فيها مفضلة الزملاء وطلبات تعديل الاتفاق.
- `ViewModels`: بيانات عرض الشاشات؛ منفصلة عن كيانات قاعدة البيانات.
- `Data/AppDbContext.cs`: تسجيل الجداول وإعداد الموديل.
- `Data/Configurations`: أنواع الأعمدة والعلاقات والفهارس والقيود المتوافقة مع SQL الحالي.
- `Data/DevelopmentDataSeeder.cs`: بيانات تطوير اختيارية عندما تكون Users فارغة فقط.
- `Migrations`: InitialCreate وSnapshot وتاريخ تغييرات EF.
- `wwwroot`: نسخة المصدر الوحيدة من CSS وJavaScript والصور المستخدمة بالموقع.

شاشات Razor تُحمّل داخل إطار الموقع الحالي للحفاظ على التصميم والتنقل. JavaScript يجلب البيانات من Controllers عبر JSON؛ كل عمليات الحفظ الحقيقية في SQL. لا تُستخدم بيانات العرض أو `js/pages.js` في تطبيق MVC.

المجلد `html` وملف `index.html` في الجذر محفوظان لتوليد Razor وتجربة العرض المستقلة؛ كلا الوضعين يستخدم ملفات `backend/wwwroot` نفسها. الأداة التالية تعيد تحويل مصادر HTML إلى Razor وتضبط مسارات الموارد تلقائيًا:

```powershell
node tools/build-razor-views.cjs
```

الأداة تعيد توليد الشاشات؛ انقل تعديل التصميم إلى مصدر HTML قبل التوليد. عند التشغيل من المشروع تُقرأ CSS وJS من `wwwroot` مباشرة؛ إعادة بناء C# مطلوبة عند تعديل Controllers أو Models أو Razor.

## ما يعمل

فلو الزملاء الجديد يشمل المفضلة المحفوظة، ودعوات 48 ساعة مرتبطة بالشقة والتواريخ، والقبول أو الرفض قبل إرسال طلب للمالك، ثم الفحص والتوقيع الفردي من كل مستأجر. تغيير الشروط يعيد الموافقات، والإيجار المؤكد ينتظر الاستلام قبل أن يصير نشطًا. مراجعة الإعلان منفصلة عن اختيار المالك للنشر، والبلاغات تحتاج قرارًا مفسرًا، وتعليق الحساب يتضمن سببًا ومدة ووضع عرض مقيّد. التفاصيل والصلاحيات في [دليل الفلو](../docs/SHARED_RENTAL_WORKFLOW.md).

الحسابات والجلسات وتغيير كلمة المرور وإبطال الجلسات القديمة، التفضيلات وملفات الزملاء، العقارات والصور والفيديو والمفضلة والتقييمات والبلاغات، التفاوض على السعر، قبول طلب الإيجار والاتفاق والفحص وتأكيد الاتفاق المباشر، الاستلام وتقارير الحالة والتسليم وإغلاق الإيجار، عروض الغرف وطلباتها، دعوات لقاءات الفيديو والردود والمواعيد، مراجعة الإدارة والإشعارات وتعليق الحسابات وسجل النشاط.

طلبات الدعم تُحفظ كسجلات موسومة `SUPPORT` داخل Activity وتظهر للإدارة في سجل النشاط؛ ليست شات بين المستخدمين ولا إرسال بريد. حد نص الطلب 1200 حرف ويُعاد رقم مرجعي.

## الخدمات الخارجية وحدود النسخة

- **رسوم النشر:** في Development توجد صفحة تأكيد اختبار صريحة دون تحصيل أموال، ويُحفظ `Simulated=true`. Production يرفض التحصيل بـ503 حتى يُضاف مزود دفع وتأكيد webhooks موثوق. المبلغ محسوب في السيرفر وإعادة التأكيد لا تضيف رسمًا ثانيًا.
- **الإيجار والتأمين:** مباشرة للمالك، دون تحصيل أو إيصالات إيجار من المنصة.
- **الفيديو:** الدعوات والموافقة والصلاحيات والوقت محفوظة وتعمل. المكالمة تعتمد على Jitsi والإنترنت والكاميرا؛ المضيف قد يحتاج دخول Jitsi. مصادقة الغرفة نفسها تحتاج مزود رموز دخول أو Jitsi خاص.
- **المساعد والفحص:** قواعد إرشادية وفحص سعر ووصف، دون ادعاء تحليل صور أو فيديو بالذكاء الاصطناعي.
- **البريد:** تغيير كلمة المرور مع معرفة الحالية منفذ؛ استرداد كلمة منسية عبر البريد يحتاج خدمة بريد ودورة استرداد منفصلة.
- **السوق:** لوحات الإدارة تقرأ SQL الفعلي، وبعض تقديرات السوق والتوافق تظل توضيحية كما يظهر في الواجهة.

هذه نسخة تطوير محلية قابلة للتشغيل والاختبار. الاستضافة العامة والدفع الحقيقي يحتاجان إعداد الخدمات الخارجية وHTTPS وشهادة SQL موثوقة، وتعطيل حسابات الاختبار.

## الحماية والملفات

Cookies من نوع HttpOnly، وفحص SecurityStamp والحساب المعلّق في كل طلب، وCSRF لعمليات الكتابة، وتحديد معدل الدخول والدعم. الأدوار والملكية تُفحص على السيرفر. العقود وطلبات الإيجار تحتفظ بنسخ تاريخية من الشروط.

عمليات الكتابة داخل معاملة Serializable وقفل تطبيق في SQL Server. فحص التوفر والتعديل تحت القفل نفسه لمنع سباقات قبول الحجوزات واللقاءات. عند التوسع يمكن تقسيم القفل حسب الموارد بدل تسلسل كل الكتابات.

الملفات المرفوعة في `backend/App_Data/uploads` ومفاتيح Cookies في `backend/App_Data/keys`. احتفظ بهما مع SQL عند النسخ الاحتياطي. الوسائط الخاصة تتطلب المشاركة أو الملكية. يُفحص الحجم والامتداد والتوقيع؛ هذا ليس ماسح برمجيات ضارة كاملًا. الملفات العامة المنشورة فقط CSS وJS والصور والفيديو، دون ملفات SQL أو مفاتيح الجلسات.

## الفحص

شغّل التطبيق أولًا للاختبارات الحقيقية:

```powershell
dotnet build backend/CampusMate.csproj
node --test tests/api.test.cjs tests/http.test.cjs tests/structure.test.cjs
node tests/backend-integration.cjs
node tests/backend-browser.cjs
```

التكامل يستخدم SQL الحقيقي وينشئ حسابات وعقارًا وسجلات اختبار مستقلة؛ لا يصفّر القاعدة، وتبقى سجلات الاختبار للمراجعة. المتصفح يحتاج Chrome وPlaywright، ويدعم `CAMPUS_BROWSER` لتغيير مسار Chrome و`CAMPUS_BASE_URL` لتغيير عنوان التطبيق. التقارير والصور في `tests/artifacts/backend`.

## تجهيز نسخة تشغيل

```powershell
dotnet publish backend/CampusMate.csproj -c Release -o output/app
cd output/app
$env:ASPNETCORE_ENVIRONMENT = 'Development'
dotnet CampusMate.dll --urls http://localhost:5080
```

أوقف النسخة الأخرى أولًا إذا كانت تستخدم المنفذ نفسه. عند تغيير المنفذ، عدّل `Campus:PublicOrigin` ليتوافق مع عنوان صفحة الدفع التجريبية.
