# قاعدة بيانات Campus Mate

المشروع الحالي واجهات HTML وCSS وJavaScript لمنصة سكن وزملاء سكن، فيها مستأجر ومالك وإدارة. ملف `data/campus-seed.json` بيانات عرض فقط؛ لا يحفظ تغييرات المستخدم. تطبيق MVC موجود الآن في `backend/`؛ راجع [دليل التشغيل](../backend/README.md).

أُعدّ `schema.sql` كبداية لقاعدة SQL Server تناسب عقد الواجهة في `docs/openapi.json` ودليل `docs/ASP_NET_INTEGRATION.md`، مع تغطية التأجير الجزئي الموجود في كود الواجهة. اختيار SQL Server يتماشى مع اتجاه ASP.NET Core الموجود أصلًا في المشروع، وليس شرطًا تفرضه الواجهة.

## التشغيل الحالي

التوثيق التفاعلي المطابق لـMasterDB الحالية موجود في [database.html](../docs/database/database.html)، ويعمل بفتح الملف مباشرة دون build أو سيرفر. يحتوي على **25 جدولًا و242 عمودًا و45 علاقة**، مع رسم ER والمخطط الكامل وقاموس الجداول وقيودها وحالاتها.

كويري الإنشاء الحالي للعرض والشرح: [MasterDB-current-schema.sql](MasterDB-current-schema.sql). يتولد من `docs/database/database-data.js`، ويحافظ على أسماء القيود والأنواع والقيم الافتراضية والفهارس الموجودة فعليًا. لا ينشئ قاعدة جديدة، ولا يحتوي بيانات حسابات، ويرفض العمل إذا كانت جداول التطبيق موجودة؛ ليس Migration ولا يُشغّل على قاعدة المشروع القائمة لتحديثها.

قُرئ المخطط من SQL Server بعملية metadata للقراءة فقط؛ استُبعد `__EFMigrationsHistory` و`sysdiagrams` لأنهما للبنية التحتية وليس لبيانات المنصة. للتحقق: `node tests/validate-database-docs.cjs` و`node tests/database-docs-browser.cjs`. كل تبويبات التوثيق تعتمد على ملف البيانات نفسه.

المشروع يعمل بالفعل كـASP.NET Core MVC، والاتصال موجود في `backend/appsettings.json`. استخدم **EF Core Migrations** لإنشاء قاعدة جديدة أو تطوير المخطط، حسب [دليل Migrations](../docs/DATABASE_MIGRATIONS.md).

`schema.sql` و`002-roommate-count.sql` مرجعان تاريخيان للمخطط السابق؛ لا تشغّلهما على MasterDB الحالية أو بعد تطبيق Migrations. إعداد API يتم من Controller داخل MVC، ولا تحتاج تعديل ملف JavaScript لتشغيل الموقع الحقيقي.

## الجداول والعلاقات

| القسم | الجداول | العلاقة |
| --- | --- | --- |
| الحسابات | Users, Preferences, RoommateProfiles, RoommateFavorites | لكل مستخدم تفضيلات وملف زميل اختياري، ومفضلة زملاء مستقلة عن الموافقة على الإيجار |
| الإعلانات | Properties, Media, PropertyMedia | المالك لديه عدة عقارات؛ لكل عقار صور وفيديو اختياري |

## قرارات التصميم

- معرّف العقار `int` يولد تلقائيًا. بقية المعرّفات نص بطول 64، بما يناسب عقد JSON؛ يمكن للباك إند توليد GUID كنص.
- النصوص البشرية `nvarchar` لدعم العربية. المبالغ `decimal(12,3)` لدقة الدينار؛ حافظ على دقة المبلغ عند تحويله إلى JSON.
- التواريخ اليومية `date` والمواعيد `datetimeoffset`. احفظ المواعيد بتوقيت UTC واعرضها بتوقيت `Asia/Amman`.
- توجد مفاتيح خارجية وقيود للقيم والفترات والأسعار وفهارس للبحث والتوفر. لا يوجد حذف متسلسل؛ حالات العقار تسمح بالإيقاف والحذف المنطقي مع إبقاء تاريخ الإيجار.
- القوائم الصغيرة كالمرافق والعادات وبنود الفحص محفوظة كـ JSON صالح. افحص شكلها وقيمها في الباك إند؛ `ISJSON` يتحقق من صحة JSON فقط.
- `PropertySnapshotJson` يحتفظ بشروط العقار وقت الطلب، و`AgreementSnapshotJson` بنص وشروط الاتفاق المقبول، و`OfferSnapshotJson` بشروط عرض الغرفة وقت الطلب. لا تُرجع سعر الإعلان الحالي بدل السعر المتفق عليه.
- الأسماء وروابط الوسائط وحقول مثل `participants`, `roommate`, `roomLabel`, `duration` للتأجير الجزئي تُشتق في DTOs من العلاقات. لا يلزم أن يطابق كل حقل في JSON عمودًا مستقلًا.
- ملف الوسيط نفسه في تخزين ملفات، و`Media.StorageKey` هو مفتاحه. ينشئ الباك إند الرابط الذي تعيده واجهة API.
- لا توجد جداول تحصيل إيجار أو إيصالات إيجار: الاتفاق والدفع بين المالك والمستأجر مباشرة. أعد `Rental.payments: []` و`paymentMethod: 'direct-to-landlord'`. الحالة القديمة `payment` في الطلب تعني انتظار تأكيد الاتفاق المباشر فقط.
- `RoommateProfiles.UserId` إلزامي في التشغيل الحقيقي. لا تستورد ملفات زملاء التجربة كحسابات وهمية؛ أنشئها لحسابات فعلية بموافقتها.
- أُزيلت جداول المحادثات والرسائل النصية. التواصل بين المستخدمين عبر لقاءات الفيديو. لا توجد حاجة لتخزين ردود المساعد أو إحصائيات السوق المشتقة كجداول مستقلة في هذه البداية.

## مسؤوليات الباك إند قبل التشغيل الحقيقي

هذه بنية أولية، وليست تنفيذًا كاملًا لقواعد العمل. يلزم في الباك إند:

- إنشاء `PasswordHash` بواسطة ASP.NET Core `PasswordHasher` أو نظام مصادقة موثوق، وتوليد `SecurityStamp` وتغييره عند تغيير كلمة المرور وإبطال الجلسات المناسبة. لا تنسخ كلمات مرور العرض إلى القاعدة. `NormalizedEmail` يُحسب بالتطبيع نفسه عند التسجيل والدخول والتعديل. جدول Users ليس مخطط ASP.NET Identity الكامل؛ إذا اخترت Identity استخدم migrations الخاصة به وأعد ربط المفاتيح الخارجية.
- فرض الأدوار والملكية: مالك العقار landlord، المستأجر tenant، وقرارات الإدارة admin. لا يسمح التسجيل العام بإنشاء admin. المفاتيح الخارجية لا تفرض هذه الأدوار.
- منع التعارض داخل معاملة واحدة عند قبول الطلبات واللقاءات؛ استخدم قفلًا ثابتًا على العقار/الغرفة أو المستخدمين بترتيب ثابت، وأعد فحص التداخل قبل الكتابة، ولا تكتفِ بفحص الواجهة أو rowversion. يُعد التداخل `existingStart < newEnd AND existingEnd > newStart`؛ آخر يوم/وقت نهاية غير شامل.
- تطبيق انتقالات الحالة، واشتقاق الأسعار والتواريخ والتأمين من بيانات السيرفر، ومنع تعديل الاتفاق بعد قبوله. التحقق من فترة عرض الغرفة ورقمها داخل الإيجار الأصلي، ومنع طلب الشخص على عرضه أو دعوة نفسه.
- إنشاء الإعلان وسجل الرسوم في معاملة واحدة. تأكيد رسوم النشر فقط بعد التحقق من توقيع حدث مزود الدفع ومبلغه وعملته وهوية العملية؛ تسجيل PaymentEvents وتحديث ListingFees ونشر الإعلان ضمن معاملة واحدة. لا تنشر إعلانًا غير مدفوع ولا تعامل رجوع المتصفح كتأكيد دفع.
- التحقق من صلاحية الوسائط وملكيتها ومحتواها وحجمها؛ عدم إرسال `RoomName` إلا للمشارك المصرح له خلال نافذة الانضمام.
- تعريف سياسة تقييمات المستخدمين، وقبول التواصل، ومراحل تقارير الاستلام والتسليم والإغلاق، والتحقق من هذه العلاقات في السيرفر.

تطبيق MVC يستخدم الجداول الحالية ويحفظ بياناته في SQL Server. تهيئة بيانات JSON للتطوير فقط تتم عبر DatabaseSetup عند خلو جدول Users. أضيف عمود Preferences.RoommatesCount لحفظ عدد الزملاء، موضح في 002-roommate-count.sql. مخطط الإنشاء ليس سكربت إعادة ضبط؛ لا تُعد تشغيله فوق الجداول الموجودة.

مرجع Microsoft: [موفر SQL Server لـ EF Core](https://learn.microsoft.com/en-us/ef/core/providers/sql-server/).
